# Requirements Document

## Introduction

本仕様書は、シフト表の売上入力における **号車の付け替え／入れ替え（売上修正）** 機能の要件を定義する。

営業日当日に予定号車が使えなくなった場合や、誤って号車を設定した場合に、管理者が後から号車を訂正できるようにする。将来の号車増設（3号車・4号車…）にも拡張可能な設計前提とする。

## Project Description (Input)

- シフト表の売上入力に「号車修正」を追加したい
- 予定号車が使えない／誤設定があるため、あとから号車を変更したい
- 管理者のみが操作できる
- 基本は付け替え（A → C）
- 付け替え先にも当日データがある場合は、確認なしで自動入れ替え（A ↔ B）
- UI は売上入力モーダル内
- 対象データは日次売上・シフト・売掛（未請求）など号車に紐づくもの一式
- 締め済み日も管理者なら変更可
- 請求済み売掛の `vehicle_num` は更新しない

## Glossary

| 用語 | 定義 |
|------|------|
| 付け替え（reassign） | 号車 A に紐づく当日データを号車 C へ移動し、A 側を空にする |
| 入れ替え（swap） | 号車 A と号車 B の当日データを相互に交換する |
| 対象号車 | 売上入力モーダルで開いている号車（操作元） |
| 変更先号車 | 管理者が選択した移動先の号車 |
| 号車データあり | その営業日に当該号車のシフトがある、または日次売上（距離・燃料・売上・経費のいずれか）が入力済み、または未請求のシフト由来売掛が存在する状態 |
| 管理者 | 既存どおりアプリにログイン済みのユーザー（`isAuthenticated`） |

## Requirements

### Requirement 1: 管理者限定の号車変更入口

**Objective:** As a 管理者, I want 売上入力モーダルから号車を変更できる, so that 誤設定や当日の号車変更を後から訂正できる

#### Acceptance Criteria

1. When 管理者が売上入力モーダルを開く, the システム shall 「号車変更」操作（ボタン等）を表示する
2. When 未ログインユーザーが売上入力モーダルを開く, the システム shall 「号車変更」操作を表示しない
3. When 管理者が「号車変更」を実行する, the システム shall 変更先号車を選択できる UI を表示する
4. When 変更先として対象号車自身を選ぶ, the システム shall 変更を拒否し、理由を表示する
5. When 締め済みの営業日でも管理者が操作する, the システム shall 号車変更を許可する（既存の売上編集権限と同じ）

---

### Requirement 2: 付け替え／入れ替えの自動判定

**Objective:** As a 管理者, I want 変更先の状態に応じて付け替えまたは入れ替えが自動で選ばれる, so that 両号車稼働時もデータが壊れない

#### Acceptance Criteria

1. When 変更先号車に当日の号車データがない, the システム shall 付け替え（対象 → 変更先）を実行する
2. When 変更先号車に当日の号車データがある, the システム shall 確認ダイアログなしで入れ替え（対象 ↔ 変更先）を実行する
3. When 付け替えが完了する, the システム shall 対象号車側の号車紐づきデータを空（または未設定）にする
4. When 入れ替えが完了する, the システム shall 両号車の紐づきデータが相互に交換された状態になる
5. When 操作が成功する, the システム shall 成功メッセージを表示し、モーダル／シフト表の表示を最新データに更新する
6. When 操作が失敗する, the システム shall エラーメッセージを表示し、部分更新のまま放置しない（可能な範囲でロールバックまたは再取得で整合を取る）

---

### Requirement 3: 号車に紐づくデータの一括更新

**Objective:** As a 管理者, I want 号車変更時に関連データが一括で追随する, so that 売上・シフト・売掛の号車が食い違わない

#### Acceptance Criteria

1. When 号車変更が実行される, the システム shall 当日の `daily_sales` における対象号車カラム群を変更先に合わせて付け替え／入れ替えする
2. When 号車変更が実行される, the システム shall 当日の `shifts.car` を付け替え／入れ替えする
3. When 号車変更が実行される, the システム shall 当日かつ未請求（`invoice_id IS NULL`）の売掛について、対象号車の `vehicle_num` を付け替え／入れ替えする
4. When 売掛がすでに請求済み（`invoice_id` あり）である, the システム shall その行の `vehicle_num` を変更しない
5. When シフトの号車が変わった結果スタッフ稼働時間が変わる, the システム shall `daily_staff_sales` の時間および `daily_sales` の人件費・現金など派生値を既存ロジックで再計算・保存する
6. When `daily_staff_sales.sales`（スタッフ別売上金額）は号車キーを持たない, the システム shall スタッフ本人への紐づきを維持し、号車付け替えの対象外とする

---

### Requirement 4: 号車増設への拡張性

**Objective:** As a 開発者, I want 号車マスタ／フィールドマップが増えても同じ操作で動く, so that 3号車・4号車追加時に UI フローを作り直さなくてよい

#### Acceptance Criteria

1. When 変更先号車を選ぶ, the システム shall ハードコードな「1↔2のみ」専用UIに依存せず、利用可能な号車一覧から選択できる
2. When `VEHICLE_FIELD_MAP`（または同等の号車→カラム定義）に号車が追加されている, the システム shall その号車を付け替え／入れ替え対象として扱える
3. When 未対応の号車番号が選ばれる, the システム shall 明確なエラーを返し、部分更新しない

> 注: 本機能の初回実装時点では既存どおり 1・2号車カラムのみが実データとして存在する想定。要件はマップ拡張で N 号車に追従できること。

---

### Requirement 5: 監査・運用上の制約

**Objective:** As a 管理者, I want 誤操作を減らしつつ必要な訂正はできる, so that 締め後・請求後の整合を保てる

#### Acceptance Criteria

1. When 号車変更前に未保存の売上入力フォーム変更がある, the システム shall 号車変更を拒否し、「先に売上を保存してください」と促す
2. When 号車変更が完了する, the システム shall 売上入力モーダルを閉じ、シフト表を最新データで更新する
3. When 配車スロット（`dispatch_slots`）等、シフト表売上以外の号車参照は本機能の対象外とする（明示的に変更しない）

---

## Out of Scope

- 複数営業日の一括号車変更
- スタッフ別人の売上金額（`daily_staff_sales.sales`）の号車間移動
- 請求済み売掛の号車訂正
- 配車ボード上の依頼スロットの車両付け替え
- 号車マスタ（車両台数）自体の追加UI（DBカラム／フィールドマップ追加は別タスク）
