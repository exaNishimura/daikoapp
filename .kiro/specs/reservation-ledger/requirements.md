# Requirements Document

## Introduction

本仕様書は、代行運転業務向けの**独立した予約台帳**機能の要件を定義する。電話等で受けた予約を配車ボード（`orders` / `dispatch_slots`）とは切り離して登録・閲覧・備忘（メモ）し、**予約当日にスタッフ向け LINE グループへ通知**する。加えて、**シフト表上で当日の予約を確認**できるようにする。顧客向け LINE リマインドは本フェーズの対象外とし、将来拡張のための方針のみ要件として残す。

## Project Description (Input)

代行運転業務向けの**独立した予約台帳**機能。配車ボード（orders / dispatch_slots）とは分離し、電話等で受けた予約の登録・一覧閲覧・メモ（備忘）を行う。必須項目は予約日時・顧客名・電話番号・メモ。スタッフ向けに予約当日のLINEグループ通知を実装する（既存の日次締め LINE 連携を流用・拡張）。顧客向けリマインドは将来拡張として設計で拡張ポイントのみ確保する。

追加確認（要件作成時）:
- ステータスは持たない。登録と削除のみ。
- シフト表に、その日の予約があれば表示したい。
- 当面の LINE 通知はスタッフ向けのみ。顧客通知は将来。

## Glossary

| 用語 | 定義 |
|---|---|
| 予約（reservation） | 配車確定前の見込み依頼。台帳上の 1 レコード |
| 予約台帳 | 予約の登録・一覧・編集・削除を行う画面群 |
| 備忘（メモ） | 予約に紐づく自由記述。顧客連絡・注意事項などを残す |
| 予約日時 | お客様が希望するお迎え等の日時（タイムゾーンは Asia/Tokyo） |
| 当日通知 | 予約日時の日付が当日である予約一覧を、スタッフ向け LINE グループへ送る処理 |
| 配車ボード | 既存の依頼・スロット配車 UI（本機能とはデータ非連携） |

## Stakeholders / Users

- **配車係 / 管理者**: 電話受注した予約を台帳に登録・閲覧・メモ追記・削除する。シフト表で当日予約を確認する
- **店舗スタッフ（LINE グループ受信者）**: 当日朝などに届く予約一覧を見て備えをする
- 認証は既存の Supabase Auth。既存アプリと同様、業務画面へのアクセス制御方針に従う

## Non-Goals（本フェーズ対象外）

- 配車ボード（`orders` / `dispatch_slots`）への自動紐付け・自動仮配置
- 顧客向け LINE リマインド・顧客 LINE ログイン
- 予約のステータス遷移（完了 / キャンセル等）。キャンセル相当は削除で扱う
- 出発地・目的地・ルート計算・所要時間見積
- 請求・売上との自動連携

## Requirements

### Requirement 1: 予約の登録

**Objective:** As a 配車係, I want 電話で受けた予約を素早く台帳に登録できる, so that 取りこぼしなく後から確認できる

#### Acceptance Criteria

1. When 配車係が予約台帳から新規登録を開始する, the 予約台帳 shall 予約日時・顧客名・電話番号・メモの入力フォームを表示する
2. When 配車係が必須項目（予約日時・顧客名・電話番号）を入力して保存する, the 予約台帳 shall 予約レコードを永続化する
3. If 必須項目が未入力のまま保存しようとした, the 予約台帳 shall 保存を中止し、どの項目が不足しているかを示す
4. When 予約が保存される, the 予約台帳 shall 作成日時を記録する
5. The 予約台帳 shall メモを任意項目として受け付ける（空文字可）
6. The 予約台帳 shall 登録した予約を配車ボードの依頼（orders）として自動作成しない

### Requirement 2: 予約の一覧・閲覧・検索

**Objective:** As a 配車係, I want 登録済み予約を日付順に一覧し絞り込める, so that 当日・翌日の備えと過去の確認ができる

#### Acceptance Criteria

1. When 配車係が予約台帳を開く, the 予約台帳 shall 予約一覧を予約日時の昇順で表示する
2. When 一覧に各予約を表示する, the 予約台帳 shall 予約日時・顧客名・電話番号・メモの有無または要約を示す
3. When 配車係が日付（または日付範囲）で絞り込む, the 予約台帳 shall 条件に一致する予約のみを表示する
4. When 配車係が顧客名・電話番号の一部で検索する, the 予約台帳 shall 部分一致で候補を絞り込む
5. When 配車係が一覧の予約を選択する, the 予約台帳 shall 詳細（全項目）を表示する
6. When 該当する予約が 0 件である, the 予約台帳 shall 空状態であることが分かる表示をする

### Requirement 3: 備忘（メモ）の編集

**Objective:** As a 配車係, I want 予約ごとのメモを追記・修正できる, so that 注意事項や連絡内容を忘れない

#### Acceptance Criteria

1. When 配車係が既存予約のメモを編集して保存する, the 予約台帳 shall メモ内容を永続化する
2. When 配車係が予約日時・顧客名・電話番号を修正して保存する, the 予約台帳 shall 変更内容を永続化する
3. When 保存が完了する, the 予約台帳 shall 更新日時を記録する
4. If 保存に失敗する, the 予約台帳 shall エラーを通知し、直前の入力内容を可能な範囲で保持する

### Requirement 4: 予約の削除

**Objective:** As a 配車係, I want 不要になった予約を削除できる, so that 台帳を正確に保てる

#### Acceptance Criteria

1. When 配車係が予約の削除を実行する, the 予約台帳 shall 確認を求め、承認後にその予約を台帳から除去する
2. When 削除が完了する, the 予約台帳 shall 一覧および詳細から当該予約を表示しない
3. If 配車係が確認をキャンセルする, the 予約台帳 shall 削除を行わない
4. The 予約台帳 shall 完了・キャンセル等のステータス項目を持たない（取消は削除で扱う）

### Requirement 5: シフト表への当日予約表示

**Objective:** As a 配車係, I want シフト表で見ている日に予約があればその場で分かる, so that シフト確認と予約備えを同じ画面で行える

#### Acceptance Criteria

1. When 配車係がシフト表で特定日を表示し、その日に予約が 1 件以上ある, the 予約台帳 shall 当該日の予約があることをシフト表上で示す
2. When 当日予約の表示領域を見る, the 予約台帳 shall 少なくとも予約時刻・顧客名が分かる一覧（または同等の要約）を示す
3. When 表示中の日に予約が 0 件である, the 予約台帳 shall 予約がない、または予約表示を出さない（誤って存在するように見せない）
4. When 配車係がシフト表上の予約表示から台帳へ遷移できる導線がある場合, the 予約台帳 shall 対応する予約または台帳画面へ案内できる
5. The 予約台帳 shall シフト表上の予約表示を閲覧用途とし、シフトデータ自体を変更しない

### Requirement 6: 予約当日のスタッフ向け LINE 通知

**Objective:** As a 店舗スタッフ, I want 予約当日にその日の予約一覧が LINE に届く, so that 出勤前に備えられる

#### Acceptance Criteria

1. When 予約当日の通知タイミングが到来する, the 予約台帳 shall その暦日（Asia/Tokyo）に属する未削除の予約を対象にスタッフ向け LINE グループへ通知する
2. When LINE 通知を送信する, the 予約台帳 shall 各予約について少なくとも予約時刻・顧客名・電話番号を含め、メモがある場合はその内容（または要約）を含める
3. If 当日の対象予約が 0 件である, the 予約台帳 shall 「当日予約なし」と分かる通知を送る、または通知をスキップする（どちらにするかは設計で確定し、運用上曖昧にしない）
4. If LINE 送信に失敗する, the 予約台帳 shall 失敗を検知し、既存の日次締め LINE 連携と同方針でリトライまたは代替アラートを行う
5. The 予約台帳 shall 既存のスタッフ向け LINE グループ連携（日次締めで利用中のチャネル）を再利用し、顧客個別への送信を本フェーズでは行わない
6. The 予約台帳 shall 同一予約当日について、同じ内容の通知を意図せず多重送信しない仕組みを持つ

### Requirement 7: 画面導線・アクセス

**Objective:** As a 配車係, I want 既存アプリのナビから予約台帳に到達できる, so that 日常業務の動線に組み込める

#### Acceptance Criteria

1. When 配車係がアプリのナビゲーションを見る, the 予約台帳 shall 予約台帳への導線を提供する
2. When 未認証ユーザーが予約台帳へアクセスしようとし、既存方針上認証が必要な場合, the 予約台帳 shall 既存の認証フローに従って保護する
3. The 予約台帳 shall 既存の配車・シフト・請求画面のレイアウトや配色を承認なく変更しない（新規画面の追加に留める）

### Requirement 8: データ分離と将来拡張（顧客通知）

**Objective:** As a 開発者 / 管理者, I want 予約台帳が配車データと分離しつつ将来の顧客通知を阻害しない, so that 段階的に拡張できる

#### Acceptance Criteria

1. The 予約台帳 shall 予約データを `orders` / `dispatch_slots` と独立した永続領域で管理する
2. The 予約台帳 shall 本フェーズで顧客向け LINE 通知を送信しない
3. Where 将来の顧客向けリマインドを追加する, the 予約台帳 shall スタッフ通知経路とは分離して拡張できる設計方針を設計フェーズで明示する（本フェーズでは実装しない）
4. The 予約台帳 shall 電話番号を顧客連絡の主キー候補として保持し、将来拡張時に参照可能な形で残す

## Open Questions（設計で確定）

1. 当日 LINE 通知の正確な時刻（例: 日次締めと同じ 08:00 JST、または別時刻）
2. 当日予約 0 件時に「なし」通知を送るか / スキップするか
3. シフト表での予約表示の具体 UI（バナー / サイドリスト / 日付セルバッジ等）— **既存 UI 変更は最小限とし、承認を得る**
